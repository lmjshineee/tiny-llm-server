## 2. 设置与执行偏差

| 项 | 值 |

| 机器 | MacBook Air Mac17,3，Apple M5，10 核 CPU / 8 核 GPU，16 GiB |
| OS / 电源 | macOS 27.3（26C5035r），AC 供电，电量 80% |

| 重复 | 单流 tg 5 次，pp/depth/CPU 3 次；batched 每个配置单次 |

正式矩阵之前跑了一次 Q4 短 warm-up；没有逐组执行事前计划要求的独立 warm-up 和固定 60 秒冷却。
没有留存温度、功耗或频率记录。因此下面是探索性测量，不能把运行间差异直接归因于热降频。
模型下载使用可变 main 引用，尚未保存仓库 revision 与文件校验和，这也是复现记录的缺口。

GGUF 报告 630,167,424 个存储参数：output 与 token embedding 分别存储。
这与共享 embedding 时约 0.494 B 的唯一参数口径不同，不表示模型变成了另一个规模。

| 量化 | 文件字节 | 张量字节减去 token embedding（估算 decode 权重读取量） |
| --- | ---: | ---: |
| Q4_K_M | 491400032 | 391859712 |
| Q8_0 | 675710816 | 525120000 |
| F16 | 1266425696 | 988208640 |

输入 embedding 按行读取；表中读取量是用于拟合的近似值，并非性能计数器测得的内存流量。

## 3. Decode 与量化

[Q4 原始数据](data/tg-q4.json)、[Q8 原始数据](data/tg-q8.json)、[F16 原始数据](data/tg-fp16.json)。
按 avg_ns / 128 计算平均步长分别为 4.378、5.584、8.540 ms。

用三个量化点拟合 `step_ms = weight_bytes / BW + intercept`，得到：

```text
BW ≈ 146.5 GB/s
intercept ≈ 1.83 ms
三个点的相对残差约 +3.0%、−3.0%、+0.4%
```

这些是仅有三个观测点、两个自由参数的解释性拟合。不同量化的反量化和 kernel 成本也不同，
所以 146.5 GB/s 不能当作独立测得的真实带宽，1.83 ms 也不能直接认定为 Metal dispatch 时间。
当前数据支持“字节量和固定成本都值得建模”，尚不足以证明各项成本的物理归因。

Q4/Q8 吞吐比为 1.277，Q4/F16 为 1.953。原预测把 H1 写成了 `tg(Q8)/tg(Q4) ≈ 1.33`，
分子分母写反：严格按原式，实测为 0.783，判定失败；若纠正为 Q4/Q8，才落在事前区间内。
不能在测完后把这个纠正计作原假设通过。

[CPU 对照](data/tg-q4-cpu.json)得到 157.0 tok/s，GPU 约快 1.46 倍。
这说明在这组小模型单流任务中，GPU 优势远小于 prefill；未单独测量两种后端的带宽与固定成本。

## 4. Prefill 曲线

[原始数据](data/pp-q4.json)：

| prompt tokens | 32 | 128 | 512 | 1024 | 2048 | 8192 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 平均 ms | 17.0 | 20.3 | 67.1 | 151.3 | 323.4 | 1969.9 |
| 平均 tok/s | 1877 | 6301 | 7632 | 6772 | 6338 | 4159 |

探索性二次拟合：`t_ms ≈ 6.4 + 0.1256*T + 1.39e-5*T²`。
1024 及以上三个测点的拟合误差小于约 1.1%，32-token 点误差约 39%。
这说明单一线性参数无法覆盖全部区间；拟合二次项占比不能等同于实际 attention 算子耗时占比。

按 Transformer 主干约 357.8 M 参数、每 token 约 2N FLOPs 粗算，pp512 对应约 5.46 TFLOPS。
这个估算省略了输出投影与 attention 等成本，不是芯片实际利用率。
日志出现 has tensor=true 只证明后端探测到支持；没有算子 trace 或禁用路径的对照实验，
**尚不能证明提速来自 M5 每核神经加速器**。之前把它写成确定原因的表述已纠正。

[留存的 CPU pp512 数据](data/pp-q4-cpu.json)为 691.2 tok/s，GPU 约快 11.0 倍。
另有一次终端观察为 640.6 tok/s，未保存完整原始输出，仅作为运行波动的提示。

## 5. 上下文与批处理

[Depth 扫描](data/tg-depth-q4.json)：

| depth | 0 | 1024 | 4096 | 8192 |
| --- | ---: | ---: | ---: | ---: |
| decode tok/s | 220.0 | 215.0 | 184.9 | 161.8 |

8k/0=0.736，即下降约 26%。KV 为 f16，约 12 KiB/token。
按上述拟合带宽计算，每增加 1024 个上下文 token，单序列 KV 字节成本约增加 0.086 ms/step。
这是近似推导；现有数据不能把剩余差异唯一归因于某个 attention kernel。

[batch1/8/16/32 一轮](data/batched-q4-32.txt)，context capacity 65536：

| batch | 1 | 8 | 16 | 32 |
| --- | ---: | ---: | ---: | ---: |
| 聚合 decode tok/s | 228.4 | 1100.0 | 1308.1 | 1213.6 |
| 每请求平均 TPOT ms（batch / 聚合吞吐） | 4.38 | 7.27 | 12.23 | 26.37 |

本轮峰值出现在 batch16，batch32 下降约 7%，同时每请求 TPOT 超过两倍。
这支持“并发增加后收益趋缓”的观察，但每配置只有一次测量，不能据此断言精确的算力天花板。

[较早的另一轮](data/batched-q4.txt)使用 context capacity 32768，batch1 基线为 198.9 tok/s。
两轮基线差约 15%，且配置与运行顺序同时变化；热状态、初始化、系统负载均是候选解释。

若把单流量化拟合外推为权重读一次、KV 随 batch 线性增加，在 ctx512 下会预测：

| batch | 近似线性外推 tok/s | 本轮实测 tok/s |
| --- | ---: | ---: |
| 1 | 220 | 228 |
| 8 | 1649 | 1100 |
| 16 | 3078 | 1308 |
| 32 | 5442 | 1214 |

batch32 相差约 4.5 倍，说明这组单流拟合不能直接外推到高并发。
这不是项目原有 synthetic-v1 的验证结果，也不证明 roofline 是唯一修正方案；后续应比较
分段曲线、算力项和调度开销，并留出测点验证。当前没有实现或启用 measured profile。

## 6. 服务端 prompt 计时与前缀复用

[保存的摘要](data/server-timings.json)来自 localhost llama-server，context4096，单 slot。
完整 HTTP 响应、生成内容和流式事件时间戳未保存。

| 请求 | prompt_n | cache_n | prompt_ms | decode tok/s |
| --- | ---: | ---: | ---: | ---: |
| 首次，无 prompt cache | 1020 | 0 | 828.653 | 194.9 |
| 再次，无 prompt cache | 1020 | 0 | 157.024 | 202.1 |
| 开启 cache 的两次请求 | 1 | 1019 | 17.732 / 6.547 | 未记录 |

首次与再次 prompt 处理时间相差 5.3 倍；原因尚未隔离。
前缀复用后只处理 1 个 prompt token，报告的 prompt 时间缩短约 9–24 倍。
后两次请求输出长度改为 8，因此不能比较完整端到端延迟。

**prompt_ms 是服务内部计时，不是客户端 TTFT。** 这次没有测量发出请求到收到第一个 token 的墙钟时间；
此前把 157 ms 和由此插值的 800-token 约 130 ms 称为实测 TTFT 不准确。
H6 的 800-token TTFT/TPOT 组合未按事前条件完成，保留为未验证。

## 7. 预测判定与项目学习价值

| 假设 | 结果 | 判定 |
| --- | --- | --- |
| H1：按原式 Q8/Q4 为 1.15–1.45 | 0.783；原预测比值方向写反 | 失败；纠正后 Q4/Q8=1.277 |
| H2：batch8/batch1 为 4.5–8 | 4.82 | 本轮落在区间内，缺少重复 |
| H3：batch16/batch8 为 0.9–1.15 | 1.19 | 本轮超出区间 |
| H4：depth8k/depth0 为 0.70–0.90 | 0.736 | 落在区间内 |
| H5：prefill 斜率 0.8–1.5 ms/token，线性 R²>0.98 | 512→2048 平均增量斜率约 0.167 ms/token | 斜率条件失败 |
| H6：800-token 客户端 TTFT/TPOT | 未按条件采集 | 未验证 |

最直接的学习收获是：

1. 区分 prefill 和 decode；同一机器的 GPU 加速比分别约 11 倍与 1.46 倍。
2. 区分单流速率、聚合吞吐和每请求 TPOT；batch16 比 batch1 吞吐高约 5.7 倍，单请求却更慢。
3. 学会拒绝单点外推；单流拟合无法可靠预测 batch32，短 prompt 线性参数也覆盖不了 8k。
4. 区分测量和解释；带宽、固定开销、算力、热降频的归因都需要额外证据。
5. 将事前预测和结果分别保存；发现比值方向写错，也应明确记录，而不是更换公式后宣布通过。

## 8. 后续与边界

这是单机探索性结果。batched 缺少独立重复，温度与频率未采集，服务数据仅留摘要，
模型版本和校验和也未固定。llama-bench 与真实服务的采样、HTTP、缓存路径不同，不能互相替代。
0.5B 的 KV 较小，但高并发长上下文仍可能产生容量压力：例如 32 个 32k 序列的 f16 KV 约 12 GiB。

下一轮优先补齐：客户端流式 TTFT、固定配置的 batched 多次重复、模型校验和与运行日志、
冷热状态的对照。之后再设计独立 measured profile，保留 synthetic-v1 默认值；
这次提交仅包含报告、预测与数据，不改变模拟器执行逻辑。
