# Calibration 02 — 模拟器 vs 真实服务：一次 24 请求突发

- 日期：2026-11-17
- 状态：**实测 + 模拟对比**。真实数据来自本机 llama-server，模拟数据来自本仓库 engine。
- 前置：[calibration-01.md](calibration-01.md)（成本模型校准）、[measure-concurrency.py](tools/measure-concurrency.py)
- 数据：[burst-real-1/2/3.json](data/burst-real-1.json)、[burst-sim.json](data/burst-sim.json)

## 0. 问题

到目前为止验证的都是**单请求成本**。项目真正的论点是调度：连续批处理比 FCFS 好。
这次的问法是：**用实测 profile 跑模拟器，能不能复现一次真实的并发突发？**

如果只能复现单请求、一并发就偏 2 倍，那这个模拟器就只能当教学工具，不能当分析工具。

## 1. 设置

| 项 | 真实 | 模拟 |
| --- | --- | --- |
| 负载 | 24 请求同时到达（8×132 / 8×523 / 8×1033 prompt，各 64 输出） | 同一组请求，arrivalTime 全为 0 |
| 并发 | `llama-server -np 8`（8 个 slot，每 slot 2048 ctx） | `maxBatchSize: 8` |
| prefill | llama.cpp 默认 ubatch 512 | `prefillChunkSize: 512` |
| 成本 | — | `measured-m5-q4-0.5b` |
| 计时 | 客户端流式，逐请求测 TTFT/TPOT/E2E | engine 内置 `RequestTimestamps` |

真实侧跑 4 次：第 1 次 4.27 s，之后三次 3.71 / 3.89 / 3.75 s。**第一次明显偏慢**（GPU 升频），
与 calibration-01 里"首个请求冷启动 5.3 倍"是同一现象，所以下面用后三次的中位数。

## 2. 结果

| 指标 | 真实（3 次中位数） | 模拟（continuous batching） | 偏差 |
| --- | ---: | ---: | ---: |
| makespan | 3.75 s | 3.30 s | −12% |
| TTFT p50 | 1524 ms | 1571 ms | **+3%** |
| TPOT p50 | 12.9 ms | 11.2 ms | −13% |
| E2E p95 | 3.74 s | 3.29 s | −12% |

同一组请求用模拟器的 FCFS 跑：makespan **9.14 s**、TTFT p50 4428 ms —— 比连续批处理差 **2.4 倍**。
真实服务没有 FCFS 模式，所以这个倍数无法在真机上验证，只能作为模拟器的内部对比。

三件事：

1. **排序结论成立**：连续批处理在这个负载下确实远好于 FCFS，模拟器给出的差距（2.4×）与排队论直觉一致。
2. **TTFT 复现到 3%**：这是最能说明成本模型正确性的一个数字——它同时依赖 prefill 的分块成本、
   排队、以及每步的 overhead。
3. **makespan 与 TPOT 偏快 12–13%**：模拟器系统性乐观，原因待查（见下）。

## 3. 那 12% 差在哪（假设，未验证）

按可能性排序，三条都可以继续测：

1. **HTTP + tokenize + 反序列化**：真实请求在进入 prefill 前有几毫秒开销，24 个请求累计在 makespan 上
   就是这个量级；模拟器没有这一项（成本模型里没有 per-request 固定成本）。
2. **prefill 抢占 decode 时间片**：真实 serving 的 chunked prefill 会打断 decode 步骤，
   造成额外的 TPOT 抖动；模拟器的混合步骤只是把两段成本相加（`calibration-01` §5.1 的 b≈8 现象）。
3. **slot 填充不完美**：24 个请求 / 8 个 slot，真实调度器在尾部会出现 slot 空转，
   而模拟器的 CB 会在每个 step 尽量填满。

第 2 条如果成立，就不是"调参"能修的，需要在 engine 里显式建模 prefill/decode 的相互占用——
这也是目前成本模型唯一还没覆盖的机制。

## 4. 局限

- **单机、单模型、单负载、单次突发**；24 个请求、一个到达模式，不能代表一般工作负载。
- 真实侧只有连续批处理一种调度；FCFS 的倍数纯属模拟结果。
- prompt 长度按 tokenize 后的真实 token 数对齐（132/523/1033），但两次运行的采样点略有差别。
- 真实侧 TPOT p50 有 12.7–15.9 ms 的run间波动（3 次），模拟器是确定性的；比较的是中位数，不是分布。
- 没有记录温度/频率；第一次运行偏慢只能归因于"冷启动"，不能证明是升频。

## 5. 结论

- 这个模拟器**可以作为分析工具**：在一个真实并发突发上，TTFT 误差 3%，makespan 误差 12%。
- 但它的绝对数字**偏乐观 10% 左右**，用于容量规划时要留余量。
- 下一步最值得做的不是继续拟合参数，而是把"prefill 与 decode 相互占用"显式建模，
  因为那是当前误差的主要候选来源，也是调度器的核心问题。
